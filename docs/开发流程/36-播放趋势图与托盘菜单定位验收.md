# V0.11.4 播放趋势图、托盘定位与窗口绘制验收

> 以下为 V0.11.4 历史记录。V0.12.4 起托盘改用卡片式自定义面板，保留 Windows 通知图标与物理像素定位；当前结果见[托盘快捷控制与卡片菜单验收](48-托盘快捷控制与卡片菜单验收.md)。

日期：2026-10-22。本交付批次从 V0.11.3 递增一次至 V0.11.4。测试期间用户追加的窗口绘制异常一并纳入本批次，不重复递增版本。

## 播放趋势图

“稳定性调整”右侧的缓冲水位、时钟漂移改为两张折线图，分别以 ms、ppm 为单位，保留当前值及有效音频包数。水位从零起算，漂移显示正负范围和零线；保留最近约 60 秒、最多 60 个采样。

后台沿用原有每秒一次的输出诊断，增加有限的数值、有效标志、采样序号和播放代次字段。UI 不解析格式化文本、不读取音频设备、不新增音频定时器；同一序号的重复 IPC 快照不重复采样。缺失／非有限数据为断点，新播放会话、停止输出或后台实例变化时清空旧轨迹，后台失联时不显示旧值为当前有效值。图表不改动缓冲策略、ASRC、UDP 时间估计或真实音频路径。

实现：`Controls/MetricTrend.cs`、`Runtime/BridgeRuntime.PlaybackMetrics.cs` 及现有快照接口。受控曲线截图的所有数据均为测试生成，不是实板采集：`ui-viewport-final/trends-controlled.png`、`trends-controlled-small.png`。

## 托盘菜单定位

当前 Avalonia 12.1.1 的 [Win32 TrayIconImpl](https://github.com/AvaloniaUI/Avalonia/blob/12.1.1/src/Windows/Avalonia.Win32/TrayIconImpl.cs) 将指针物理坐标、主屏缩放和屏幕矩形混用于托盘弹出窗口定位；这是原菜单在混合 DPI 显示器上远离图标的源码原因。本批改用 Windows 通知图标和原生 HMENU：指针／托盘图标矩形与菜单位置始终使用屏幕物理像素，按实际显示器工作区约束，无主屏缩放换算。

通知图标保留原应用图标、状态提示、左键打开主窗口及原有菜单操作；Explorer 重建通知区域时重新注册。原生菜单由 Windows 处理键盘导航、点击取消、显示器边缘及 DPI，退出仍只有一个，保持 V0.11.3 的统一退出规则。没有新增 WinForms 或其他图表／托盘依赖。

API 依据：[TrackPopupMenuEx](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-trackpopupmenuex)、[Shell_NotifyIconGetRect](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/nf-shellapi-shell_notifyicongetrect)。

实际菜单定位检查使用本机三台显示器：缩放 125%、150%、200%，含负屏幕坐标。每台测量靠近左上和右下工作区的两个锚点，共六个真实 Windows 菜单窗口。19 项检查通过，菜单与锚点距离为 0–1 个物理像素，全部位于对应工作区内；证据 `native-tray-final/native-tray-placement.json`。该检查自动弹出并关闭隔离预览进程的菜单，没有移动鼠标或操作用户原程序。

## 测试过程中窗口持续局部绘制

用户反馈“始终异常，直到调整窗口”。已复现：初始打开时原生窗口 DPI 为 120（125%），但客户区／框架后台仍保留另一缩放比例的尺寸。原生客户区比实际绘制区域宽 **350 px**、高 **216 px**；跨屏移动触发完整 DPI 更新后恢复。修改前证据：`window-scaling-baseline/window-scaling.json`。这不是仅凭截图猜测的缩放问题，也没有把空字段直接判断为设备配置丢失。

窗口启动、缩放变化、位置变化及托盘恢复时，合并排队核对原生客户区、Avalonia ClientSize 和根布局；只有实际不同步时才修正。先重送当前真实尺寸；若后台自身仍保留错误 DPI，则使用当前窗口 DPI 和原有外框矩形通过正常 Win32 DPI／尺寸路径同步，再重新布局和绘制。不修改系统缩放、不关闭 GPU 加速、不反射修改框架私有字段，也不通过人为增加／减少一像素窗口大小绕过问题。尺寸正常时立即返回，避免拖动窗口时反复强制全量布局。

修改后验证启动、三种 DPI 间两轮移动／隐藏恢复、最大化和还原，共 **15 个场景**；原生像素尺寸与根布局×缩放的偏差全部为 **0 px**。证据：`window-scaling-final/window-scaling.json`。首轮只补尺寸通知未修复的记录保留在 `window-scaling-after`，后续同步后台 DPI 的通过记录另存，没有覆盖失败窗口。

同时修复测试窗口干扰桌面的行为：主验收窗口不激活、不进入任务栏，并在显示后移到屏外，避免框架把初始屏外位置重新规范到可见屏幕。EngineUiChecks 补齐同样的启动约束；窗口恢复时的测试回调只运行一次，防止重复进入验收。专门的跨屏检查显式允许显示，但将窗口置于其他窗口之后；正常产品窗口的交互不使用这些验收限制。

## 结果与边界

证据根目录 `artifacts/acceptance/v0.11.4`。最终汇总以同目录 `software-delivery.json` 为准。

| 验证 | 结果 |
| --- | --- |
| 编译与协议／音频离线 | 固件、前台与 Engine 构建发布通过；1231 项现有离线检查通过。最终 App 在窗口修复后重新发布 |
| 原生界面与趋势图 | 319 项通过；包含 60 点容量、正负漂移、重复序号、缺失／NaN 断点、代次清空及 1050×680 小窗口 |
| Windows 原生菜单 | 19 项通过，三台显示器六个位置的真实 HMENU 几何测量 |
| 窗口 DPI 与客户区 | 15 场景通过，启动／跨屏／恢复无需手动调整大小，尺寸偏差 0 px |
| 生命周期、独立 IPC、发布启动 | 80 项生命周期、632 项独立 IPC、10 项实际发布检查通过；最终报告分别为 `lifecycle-release/result.json`、`engine-ui-delivery/result.json`、`published-delivery.json` |

生命周期复验中还捕获到测试启动器的加载竞争：子进程刚创建时 `MainModule` 可为空，过早读取导致空引用，随后保留了错误的预期路径并持续拒绝握手。改为等待管道服务就绪后刷新并读取实际模块路径；PID、路径、启动时间、会话及版本校验保持严格，错误原因分开记录。失败日志和 IPC trace 保留在 `lifecycle-final`、`lifecycle-verified`，最终复验另存 `lifecycle-release`。

统一构建的一个窗口在原有“worker interval instrumentation allocates zero steady bytes”检查处失败；该被测音频代码及门槛均未修改，失败日志 `artifacts/trend-tray-build-final.log` 保留，复跑通过日志为 `artifacts/trend-tray-build-verified.log`。没有凭一次失败或重跑结果断言其根因。

本批没有刷写固件、执行 COM8 联调、真实音频录放或物理耳机验收。图表截图为受控数值，菜单和窗口测量为真实 Windows 几何结果，二者均不替代实板音频验收。前批上下曲的真实 Host 复验仍待完成。
