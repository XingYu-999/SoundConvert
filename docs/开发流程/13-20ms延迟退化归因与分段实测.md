# 20 ms 延迟变化归因与分段实测

日期：2026-10-19，Asia/Shanghai。结论：本轮新增延迟的主要来源是 **USB FIFO 余量和 PC 预填充/起播水位策略**，不是 PCM 解码或重采样计算性能不足。共享 WASAPI 的既有输出排队还需要单独预算。当前共享 20 ms 档本次短测连续性计数正常，独占 96k 两组仍有异常；均未证明音源到耳机的物理延迟低于 20 ms。

## 一、先对齐比较条件

- 用户要求继续以有线和指定 Realtek 耳机测量。输入固定为 Windows USB 48 kHz/16-bit；96 kHz/24-bit 输出使用明确独占格式，不改变共享格式或系统默认输出。
- 六组新测试每组正式 30 秒、预热 2 秒，顺序为共享 20 ms 的旧→新、共享 80 ms 的新→旧，再测当前独占 96 kHz。旧软件 V0.0.9 Core 与当前 V0.1.0 Core 都加载原有冻结 DLL。**两者固件均为已烧写的 V0.1.0**，因此这是隔离 PC 差异的 A/B，板端改动另用源码/旧 ELF 和原始记录核实。
- 网卡保持用户已批准的两个试验参数：InterruptModeration=0、EnableK1=0；不改 IP。此处不把网卡试验效果冒充代码改进。环境信息见 `latency-audit/environment.json`。
- 20/80 ms 是应用源索引缓冲的**上限**，不是总延迟；实际预填充、已排队输出、输入 USB 和传输各自计量。
- 已复核历史 V0.0.3 两条 48k 转换通过记录：当时为 **80 ms 上限、41.5 ms 预填充、22 ms 实际 WASAPI 缓冲**；包括 N300 与 Realtek 输出。更早 `network-playback-20ms-v3.jsonl` 则有欠载 1、溢出/重同步 9。现存记录没有物理端到端低于 20 ms 的测量。这不否定用户观察到的早期低延迟体验，但不能据这些记录声称已做同条件物理对照。

## 二、哪些改动增加了等待

| 改动 | 升级前 | 当前 | 对延迟的作用与证据 |
| --- | --- | --- | --- |
| USB FIFO 反馈目标 | 2 ms，48/16 阈值 384 B | 6 ms，阈值 1152 B | 稳态积压目标增加约 **4 ms**。旧 V0.0.5 ELF 回调反汇编及冻结 V0.0.9 源码均核实；当前实板 FIFO 分布集中于读取前 6–7 ms。FIFO 水位是源样本跨度，不是已逐样本打点的 USB 驻留时间。 |
| 80 ms 档保守预填充 | 41.5 ms | 通常 56 ms | 代码明确多等待 **14.5 ms**；这是为覆盖到包停顿增加的余量。`MaximumBufferMs < 40` 时该保守下限为 0，故不能拿这条解释 20 ms 档全部变化。 |
| 起播后的漂移参考 | 动态 targetFrames | 实际起播水位 driftReferenceFrames | 修正假漂移，但也**保留了起播超出目标的积压**：当前只裁到接近硬上限的 ceiling，没有强制对齐目标 prefill。相同当前 DLL 的 10 秒预检驻留 P50≈12.008 ms，正式 30 秒运行≈19.042 ms；起播相位/批量到包不同，稳态驻留可相差约 7 ms。不能把单次差异全部归因于滤波器。 |
| 默认 sinc 质量 | 48 taps，48k 前瞻 0.5 ms | 均衡 96 taps，48k 前瞻 1 ms | 需要额外 **0.5 ms 未来数据**；低延迟档仍为 48 taps/0.5 ms。此前瞻已体现在缓冲需求中，不能在实测驻留后重复相加。 |
| 抖动记忆 | 每包 .9999 衰减、忽略 >50 ms 间隔 | 按时间 10 秒衰减，保留长停顿 | 更长停顿会提高后续起播/重缓冲需求；活动播放时不直接因 recommendation 增长而追加等待。 |
| WASAPI 请求/实际输出缓冲 | 请求 10 ms，共享实际 22 ms | 相同 | **没有发生 10→22 ms 的本轮回退**；旧记录已有 22 ms。新诊断共享播放时 CurrentPadding 通常约 12 ms，这部分在应用缓冲之外。 |

关键源码：`SoundConvertBoard/usb/usb_timing.h`、`usb/usb_audio.c` 的反馈回调与 consume；`SoundConvertClient/Core/AudioBuffer.cs` 的 ConservativePrefillMs、requiredPrefill、prefillCeiling 和 driftReferenceFrames；`Core/SincFilter.cs` 的质量选择；`App/WindowsAudio.cs` 的 WasapiOut 初始化。

额外用冻结 DLL 做确定性模型验证：固定 1 ms 输入、10 ms 输出，分别从 12 ms 和 19 ms 起播；当前版本两者的目标都为 12 ms，但虚拟 60 秒后读取前水位仍分别为 12 ms 和 19 ms，漂移参考也分别为 12/19 ms、估计漂移 0 ppm。即 **7 ms 额外驻留在没有网络抖动、CPU 负载或真实漂移时也能复现**。这是源代码归因的直接证据，原始结果为 `latency-audit/model-current.jsonl`；它是离线模型，不冒充实板测量。

完全相同模型在旧 V0.0.9 DLL 上，从 19 ms 起播后虚拟 60 秒水位回到约 **12.479 ms**；当前保持 **19.000 ms**。所以除了稳态 FIFO/高余量档变化，确有本轮 PC 代码造成的额外驻留保持。旧策略借漂移环来追目标也会造成假漂移，修复应在起播阶段选择水位，不能简单恢复旧漂移误差定义。两份模型日志均保留。

没有证据支持以下解释：环形存储 16384→32768 自动增加固定延迟；UDP 接收缓存 256 KiB→1 MiB 自动等待填满；48→96 kHz 必然使音频时长翻倍；24-bit 扩展需要收集更长时间；FEC 必须攒四包才能播放原包。上述存储是容量，原始 PCM 包仍立即处理。

## 三、按用户要求分段

### 1. 开发板接收音源与处理

当前没有数字调制或压缩编码：USB PCM → FIFO → 每 1 ms 提取 → 主音量/静音 → 包头与原始 PCM → W5500。

最明确新增等待为 FIFO 2→6 ms。启动仍在至少两块数据后 prime，并未改成必须等满整个 12352 B FIFO。4 ms 是**提取后块年龄丢弃上限**，不是固定等待 4 ms。满增益/静音已有快路径；1 ms 音量渐变处理当前块的样本，不额外排队一个块。

已有实板指标记录提取后到 Core 1 取块峰值约 2.446 ms、USB 关中断区峰值 72 μs、USB 活动服务间隔峰值 428 μs；这些是不同事件/累计最大值，不能相加作为某一包总耗时，也不能把服务间隔等同于 DSP 函数耗时。**目前没有单独覆盖 USB 接收首样本→提取→音量处理→SEND 的逐包时间戳，DSP 纯执行时间不能伪造。**下一步需要在板端同一微秒时钟下分别打点；ISR 不打印日志或发送网络。

### 2. UDP 传输

音频块仍为 1 ms，原始包立即提交；FEC 为每四包额外发一包。SPI 10→25 MHz 缩短搬运时间，SENDOK 所有权检查防止上一包未完成时覆盖，并非额外设定十几毫秒延时。

新实板 UDP PROBE 往返数据见下表，PC 以同一 QPC 测量，包含双向链路、板端回声服务和 Windows 交付。它支持“正常传输不是几十毫秒固定计算成本”，**不能当成精确单向值，也不直接除以二**。48/16 每包 240 B UDP payload，W5500 100 Mb/s 链路含以太网开销的理论串行化约 24.48 μs；这是计算值，不是实测单向传输。

此前 89 ms 事件在 Npcap 驱动时间戳和应用都可见，且没有 GC 停顿、USB 或板端丢弃计数；这是交付长尾证据，不能直接称为网线传输用了 89 ms，更不能称为 CPU/带宽性能不够。需要逐包板端时间戳、驱动交付与应用到达联合定位。没有精确时钟同步时，不把板端微秒时间和 PC QPC 直接相减。

“加 CurrentPadding”是回调时端点队列的估算，**不是音源→耳机的实测端到端值**，不覆盖源端 WASAPI、USB、socket 交付和 DAC。不要把 22 ms BufferSize、StreamLatency、CurrentPadding 三项再全部相加；也不要把 ASRC 前瞻在已测驻留上重复增加。

## 四、针对低于 20 ms 的改进顺序

1. **先约束起播水位**：保留纠正假漂移的参考分离，但在未播放的起播/重缓冲阶段按目标 prefill 加一包余量选择源游标，显式记录被跳过的启动帧；不要只裁到接近 MaximumFrames。这样可避免 12 ms 需求起播到 19 ms 后永久保持。活动播放仍不偷偷丢帧。先用不同回调相位和 1/5 ms 到包批量做确定性回归，再上耳机 A/B。
2. **降低实际输出周期**：现有共享路径的额外队列约 12 ms。先评估 IAudioClient3 支持的最小共享周期，或提供明确独占低延迟输出；读取实际支持周期/缓冲和 underrun，不能仅把 WasapiOut 的请求从 10 改成 3 就声称生效。当前 96/24 独占对照帮助区分共享排队。
3. **分开游戏低延迟档与高余量档**：80 ms/56 ms 预填充不能作为低于 20 ms 的完成方案。低延迟档应给 USB、网络/抖动和实际输出各自预算，默认仍受用户明确选择约束，不自动改到 80 ms。
4. **板端 FIFO 做专门低延迟配置再验收**：当前 6 ms 是为 Windows Host 曾出现约 3.883 ms RX 停顿增加的余量；直接退回 2 ms 有连续性回退风险。先测 NS2 的 48/16 供数、反馈响应和 FIFO 低水位，再决定 2/3/4 ms 目标，分别记录稳态驻留与 USB 欠载。用更大的物理容量接突发并不要求提高稳态目标。
5. **滤波器保持可选择**：48/16→96/24 的低延迟 sinc 只需 0.5 ms 前瞻。均衡额外 0.5 ms 不是首要矛盾，不应为节省几十微秒处理时间牺牲已验证的抗混叠。
6. **分别验收**：20 ms 缓冲档的无爆音连续性、各段处理/驻留、物理端到端 <20 ms 是三项指标。物理验收需要同一参考信号的输入/输出双通道采集或等效校准；当前证据无法代替该测试。

本次只新增诊断工具和记录，产品 App/Core 与已烧写固件未改动，端点音量/静音已恢复，没有把 80 ms 写入用户设置。当前 VERSION 保持本交付批次 V0.1.0，不重复加版本。NS2 实机仍待接入。
