## 联调中修复的问题

1. 上游 ioLibrary IPv4 非阻塞 `recv()` 在检查有数据之前就返回 `SOCK_BUSY`，TCP 虽连接成功但 HELLO 超时。已记录独立补丁并完成真实认证回归。
2. DAPLink 烧写后的运行启动改为明确 `reset halt; resume`；原镜像保留，烧写逐次校验。
3. Core1 默认栈不足，改为普通 SRAM 中独立 16 KiB 栈；Flash 链接区限制为实际 2 MiB 减配置 8 KiB。
4. 随机 uint32 流 ID 的科学计数 JSON 和大于 `INT_MAX` 的解析已修复。
5. 无效连接改为有期限的非阻塞 DISCON，客户端能收到结束；大响应重试使用紧凑缓存，不重新生成流标识。
6. 周期 UART 同步打印会阻塞网络消费，改为 FIFO 分段非阻塞输出；增加过期/旧代次帧与 SENDOK/timeout 计数。
7. 真实音量检查发现主音量加声道音量导致 Windows 的 −20 dB 设置实际约 −40 dB。首版收敛为仅主音量/静音，左右 PCM 声道保持不变；不再宣告无须提供的声道控制。测试须核对实际增益比例，而非仅判断“音量变小”。

此前约 7 分钟 v4 预跑和因修复音量问题主动结束的 v6 预跑均保留，均不冒充完整长测。此次完整测试验证 USB → 以太网接收连续性，不等于 ASRC/WASAPI 播放也已连续运行 30 分钟。

## 性能和验收边界

- 本机 Realtek 共享输出请求 10 ms，但 API 实际缓冲为 1056 帧、22 ms；常规回调 10 ms，首次可为 22 ms。上位机明确记录这些值，默认抖动缓存上限 20 ms，超限回调输出静音并计数，不暗中扩大。
- 48-tap、1024 相位 sinc ASRC 前瞻 24 帧，约 0.5 ms。离线幅频和人工漂移回归不等于实测端到端延迟或完整听音评价。
- Windows USB 与本机局域网已测；NS1、NS2、手机、其它路由器、VLAN、多个物理 PC、真实睡眠恢复、物理掉电和热拔插需相应硬件场景。不能把当前 PC 模拟音源结果写成游戏主机兼容通过。
- 未完成 2 小时/24 小时发布压力测试、USB 线上反馈抓包、模拟挂起功耗、物理端到端延迟和干净机安装验收。
- 当前不实现 UAC2、录音回传、远程固件升级、业务端口编辑、恢复出厂和任意 USB 格式修改；对应能力明确不支持，不接受“保存成功但无效果”。
- Wi-Fi 传输可能丢包；USB 连续性、网络包缺口和 WASAPI 播放分别统计，不宣称网络 bit-perfect。

96k/24/2原始PCM为4.608Mbps；USB最大包582B/1ms低于Full-Speed每帧1023B限制，FIFO分配2328B，feedback目标1152B约2ms。UABA每ms为96帧、576B PCM加48B头，共624B；当前9.375MHz SPI仅搬运这些包已约53%占用，控制/寄存器/S0流量仍需实测余量。`format_selected`表示Host选择了非零alt，不等于正在播放；挂起或重新预填充时可以selected=true而streaming=false。代次切换、未知短块和超期不会拼接旧PCM。

## v10 控制轮询导致的过期整改与 v11 诊断边界

v9在新接收器每500ms查询GET_INFO的20秒实测中，发生27个源索引缺口、1296帧缺失，与板端`usb_expired_frames`增量1296完全一致；USB FIFO欠载、重同步和队列满增量为0。此结果不能归因于Wi-Fi。证据：`audio-v9-96k-no-spatial.jsonl`；该轮实际格式仍是16/48。

代码审查发现每次GET_INFO新增的Q8.8小数会进入cJSON通用`%g`格式化及`sscanf`回读路径，控制工作还与音频串行累积。v10为uint32和精确Q8.8加入纯整数十进制输出，保留其JSON数值类型；每轮优先处理音频，并在控制槽之间再次服务音频。4ms过期阈值、队列容量和反馈水位均未放大。所有合法USB Q8.8值及边界向量已用实际生产cJSON逐值往返验证，共30750次检查。

v10镜像 `board-v10-audio-scheduling.elf` SHA256：

`5BA00E4593657288FE56CF75D856C1CD2C20228CE9F1BBC8E9E0BB93286C3E3B`

同类500ms INFO的20秒对照通过：961872帧，gap=0、missing=0，板端expired/queue/underrun/resync增量均为0。活动流poll最大4961µs、单控制段最大2793µs；音频在段间被服务，不能把整轮poll最大值直接等同音频连续阻塞时间。证据：`audio-v10-control-poll-stress.jsonl`。这证明当前16/48控制负载下的板端过期问题已改善，不证明全部高规格或系统压力场景无爆音。

随后30秒Realtek实际监听出现一次不同问题：USB underrun/resync各增加1，generation由6变7，发生在约8.8秒；expired仍为0、运行USB服务间隔最大342µs。源100秒仍在持续，故不能直接当作正常停播。该轮频谱目标能量比例通过，但发生重建与播放欠载，整轮连续性未通过。证据：`monitor-v10-48k-80ms.jsonl`、`source-v10-48k.jsonl`。

v11仅增加欠载现场诊断，不改变FIFO/反馈/调度/短块策略：GET_STATS的`usb_fifo_diagnostics`记录最近欠载的available/read/wanted字节、距最后USB RX时间、USB服务间隔和发生时刻，以及RX最大间隔、最近包长和最小消费水位。目的是区分正常反馈帧数摆动碰到消费相位，还是Host/驱动实际断送；未获得现场数据前不盲目扩大缓存。v11待诊断镜像SHA256为`23F702A09CF5EE12235DDD227E3D4A76B095BE165014D8479EA88A6C0D9E6F61`，USB生产回归增至98项；真实结果由后续记录补充。

## 2026-10-19：Windows 分段测试音截断修复（最终统一 V0.0.5）

### 原因与改动
