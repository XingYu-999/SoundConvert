## 二层问题的实际原因与验证

原搜索接口过滤可由 Windows GUID 找到 Npcap 接口，但 `RefreshL2Peer` 等后续代码使用字符串完全相等判断 `AdapterName == adapter.Id`。同一网卡的两种名称不相等，导致已发现设备在打开设置时误报未找到。现在统一去除 Npcap 前缀、规范 GUID 并忽略大小写；不使用子串匹配，不放宽设备 ID、MAC、网卡、boot 或 revision 校验。

实际测试主机为当前电脑，明确绑定以太网 `192.168.8.74`、Intel I219-V，目标为截图中的 `192.168.8.73:49161`，DeviceId `aa36483cef4256f169f4f4e5322c6df8`。IPv4、Npcap 均发现同一台设备；生产 Runtime 的统一搜索合并为一行，状态包含 Npcap 提示，随后重新发现并成功解析出新鲜配置身份。测试使用隔离电脑配置，没有 TCP 管理连接、设备 IP 写入或电脑网卡配置修改。

证据：`artifacts/acceptance/v0.11.1/live-discovery-final/discovery.json`，7 项通过。设备读回固件仍为 **V0.11.0**。

## 上下曲修复的证据边界

前台命令、Engine 分发、协议字符串和原 usage 定义核对正确。原 HID 描述符声明 Consumer usage `0..0x3FF` 的数组，覆盖大量未实现控制；本批次改为仅声明六个独立控制位，报告仍为两字节、释放仍为全零，传输状态 `last_usage` 仍报告 usage。bit0..5 对应播放暂停、下一曲、上一曲、音量加、音量减、静音。正式描述符修订为 `0x0800`，可选状态通知原型为 `0x0900`，与旧报告布局区分。完整接口、UAC1、四预设及 Consumer 兼容开关保持。

HID usage 语义参考 [Android 内核 hid-input.c](https://android.googlesource.com/kernel/common/+/refs/heads/android-mainline/drivers/hid/hid-input.c)；有限位图和六种 usage 的对应由实际 ELF 与生产状态机检查共同核对。**没有在本轮刷入新固件，尚未证明用户所用真实 Host 上的上下曲行为已经恢复**；宽范围描述符是否就是该 Host 误映射的原因，也不能由离线检查单独证实。需刷入本批配套固件、重新枚举后，分别确认上下曲改变播放器曲目且不改变音量，音量加减及其他键仍正常。
